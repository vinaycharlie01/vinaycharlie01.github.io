Golang Trap Questions: Tricky Go Code Examples Every Developer Should Understand ​

Introduction ​

Go is famous for being a small, simple language. And most of the time it is. But there are a handful of places where Go behaves in a way that surprises even experienced developers — shared slice backing arrays, typed nil interfaces, defer argument evaluation, loop variable capture, and channel deadlocks.

These are exactly the cases interviewers love. They look easy on the surface, but they reveal whether you truly understand how Go works under the hood, or whether you have just memorized syntax.

This post walks through the most common Go trap questions. For each one you get a small runnable snippet, the question, the output, and a plain-English explanation of why it happens. The examples assume a modern Go toolchain; where behavior changed between Go versions, I call that out explicitly.

Common Golang Trap Questions ​

1. Slice Sharing and Underlying Arrays ​

The Code

go
package main

import "fmt"

func main() {
	a := []int{1, 2, 3}
	b := a[1:3]

	b[0] = 99

	fmt.Println(a)
}

The Question

What does this print?

The Output

[1 99 3]

The Explanation

b := a[1:3] does not copy the data. It creates a new slice header that points into the same underlying array as a. So b[0] and a[1] are the same memory location. Writing 99 through b changes what a sees.

The Common Misconception

Thinking that slicing creates an independent copy.

The Takeaway

Slices are views over a shared array. If you need an independent copy, use copy(dst, src) or append([]int(nil), src...).

2. Slice Length, Capacity, and append() ​

The Code

go
package main

import "fmt"

func main() {
	a := make([]int, 2, 4)

	b := append(a, 1)
	c := append(a, 2)

	fmt.Println("a:", a)
	fmt.Println("b:", b)
	fmt.Println("c:", c)
}

The Question

What is the value of b after c is created?

The Output

a: [0 0]
b: [0 0 2]
c: [0 0 2]

The Explanation

a has length 2 and capacity 4, so it has two spare slots. Both append(a, 1) and append(a, 2) fit without allocating a new array, so they both write into the same backing array at index 2. The second append overwrites the first, and b sees that change too.

The Common Misconception

Assuming append always copies or that b is frozen at [0 0 1].

The Takeaway

When the capacity is large enough, append reuses the existing array. Slices created from the same backing array can affect each other.

3. Nil Slices vs. Empty Slices ​

The Code

go
package main

import (
	"encoding/json"
	"fmt"
)

func main() {
	var nilSlice []string
	emptySlice := []string{}

	nilJSON, _ := json.Marshal(nilSlice)
	emptyJSON, _ := json.Marshal(emptySlice)

	fmt.Println("nilSlice == nil:", nilSlice == nil)
	fmt.Println("emptySlice == nil:", emptySlice == nil)
	fmt.Println("nil JSON:", string(nilJSON))
	fmt.Println("empty JSON:", string(emptyJSON))
}

The Question

Are a nil slice and an empty slice the same thing?

The Output

nilSlice == nil: true
emptySlice == nil: false
nil JSON: null
empty JSON: []

The Explanation

Both have length 0 and capacity 0, but they are not the same value. A nil slice has no backing array and is equal to nil. An empty slice is a non-nil slice that points to a zero-length backing array. This difference matters for JSON: a nil slice marshals to null, while an empty slice marshals to [].

The Common Misconception

Believing that len() == 0 always means the slice is nil.

The Takeaway

Use slice == nil when the distinction matters — for example, when you need to return [] instead of null from an API.

4. Nil Maps and Map Assignments ​

The Code

go
package main

import "fmt"

func main() {
	var m map[string]int

	fmt.Println("read:", m["missing"])

	m["x"] = 1
}

The Question

What happens when this code runs?

The Output

read: 0
panic: assignment to entry in nil map

The Explanation

Reading from a nil map is safe and returns the zero value for the value type. Writing to a nil map panics because there is no map to store into.

The Common Misconception

Assuming both reads and writes are safe, or that Go auto-initializes the map.

The Takeaway

Initialize maps before writing with make(map[string]int) or a map literal.

5. Interface Values and Typed Nil Pointers ​

The Code

go
package main

import "fmt"

type MyError struct{}

func (e *MyError) Error() string {
	return "boom"
}

func doSomething() error {
	var err *MyError
	return err
}

func main() {
	if err := doSomething(); err != nil {
		fmt.Println("error:", err)
	} else {
		fmt.Println("no error")
	}
}

The Question

Does this print no error, error: boom, or something else?

The Output

error: boom

The Explanation

doSomething returns a typed nil pointer converted to the error interface. An interface value is only nil when both its dynamic type and its dynamic value are nil. Here the type is *MyError (non-nil) and the value is a nil pointer, so err != nil is true. When fmt calls Error() on the nil receiver, the method does not dereference the pointer, so it returns "boom" without panicking.

The Common Misconception

Thinking a nil pointer returned through an interface is a nil interface.

The Takeaway

Return a plain nil (return nil) from functions that return error, never a typed nil pointer.

6. defer Execution Order ​

The Code

go
package main

import "fmt"

func main() {
	defer fmt.Println("first")
	defer fmt.Println("second")
	defer fmt.Println("third")

	fmt.Println("main")
}

The Question

In what order do the deferred calls run?

The Output

main
third
second
first

The Explanation

Deferred calls run in last-in, first-out (LIFO) order when the function returns.

The Common Misconception

Assuming deferred calls run in the order they were registered.

The Takeaway

Think of defer as a stack. This is useful for pairing open/close or lock/unlock operations in reverse order.

7. Evaluation of Deferred Function Arguments ​

The Code

go
package main

import "fmt"

func main() {
	x := 1
	defer fmt.Println("deferred:", x)

	x = 2
	fmt.Println("before return:", x)
}

The Question

What value does the deferred call print?

The Output

before return: 2
deferred: 1

The Explanation

The arguments to a deferred function are evaluated when the defer statement is executed, not when the function actually runs. At defer time, x is 1, so 1 is captured. Changing x later does not affect the already-evaluated argument.

The Common Misconception

Believing the deferred call reads the latest value of x.

The Takeaway

defer fmt.Println(x) captures the current value. Use a closure if you want the value at return time.

8. Named Return Values and defer ​

The Code

go
package main

import "fmt"

func f() (result int) {
	defer func() {
		result++
	}()
	return 1
}

func main() {
	fmt.Println(f())
}

The Question

What does f() return?

The Output

2

The Explanation

Because the return value has a name (result), the return 1 assigns 1 to result. Then the deferred closure runs and increments result to 2 before the function actually returns to its caller.

The Common Misconception

Thinking the deferred call runs too late to change the return value.

The Takeaway

A deferred closure can modify named return values. This is often used to wrap or record errors.

9. Closures and Loop Variables ​

The Code

go
package main

import (
	"fmt"
	"time"
)

func main() {
	for i := 0; i < 3; i++ {
		go func() {
			fmt.Print(i)
		}()
	}

	time.Sleep(time.Second)
	fmt.Println()
}

The Question

What does this print?

The Output

This depends on the Go version.

  • Go 1.22 and later: each iteration gets its own i, so the output is a permutation of 0 1 2 — for example 012, 120, or 210. The order is nondeterministic, but each value appears exactly once.
  • Go 1.21 and earlier: i is a single variable shared by all iterations. By the time the goroutines run, the loop has usually finished and i is 3, so the output is typically 333. This is a data race, so the exact output is not guaranteed.

The Explanation

Before Go 1.22, the loop variable was created once and reused for every iteration. Each closure captured a reference to that same variable, not a copy of its value. Go 1.22 changed the rule so each iteration gets a fresh variable.

The Common Misconception

Assuming each goroutine gets its own copy of i, which was only true from Go 1.22.

The Takeaway

Pass the value as an argument to be safe on every Go version:

go
for i := 0; i < 3; i++ {
	go func(n int) {
		fmt.Print(n)
	}(i)
}

10. Goroutine Scheduling and Nondeterministic Output ​

The Code

go
package main

import (
	"fmt"
	"time"
)

func main() {
	go fmt.Print("A")
	go fmt.Print("B")
	go fmt.Print("C")

	time.Sleep(100 * time.Millisecond)
	fmt.Println()
}

The Question

Will the output always be ABC?

The Output

Not guaranteed. Any permutation of A, B, and C is possible, such as ABC, BCA, or CAB. You may also see the same letters in different orders across runs.

The Explanation

The go keyword starts each call as a separate goroutine. The Go scheduler decides when each goroutine runs and on which thread. Nothing in this program forces an order. The time.Sleep only keeps main alive long enough for the goroutines to run. It is not a synchronization tool.

The Common Misconception

Assuming goroutines run in the order they were started, like function calls.

The Takeaway

If order matters, coordinate with channels or sync.WaitGroup. Never use time.Sleep as a way to wait for work to finish.

11. Buffered vs. Unbuffered Channels ​

The Code

go
package main

import "fmt"

func main() {
	buffered := make(chan int, 1)
	buffered <- 1
	fmt.Println(<-buffered)

	unbuffered := make(chan int)
	unbuffered <- 1
	fmt.Println("never printed")
}

The Question

What is printed, and what happens on the second send?

The Output

1
fatal error: all goroutines are asleep - deadlock!

The Explanation

A buffered channel with capacity 1 can hold one value without a receiver, so buffered <- 1 succeeds. An unbuffered send blocks until another goroutine is ready to receive. Here only main exists, so nothing can ever receive, and the runtime reports a deadlock. Note that this is a runtime failure, not a compile error.

The Common Misconception

Thinking a send on any channel is non-blocking, or that a buffer of size 1 means "always safe to send" no matter what.

The Takeaway

Unbuffered channels are a handshake: both sides must be ready at the same time. Buffered channels only help when the buffer has room.

12. Channel Deadlocks ​

The Code

go
package main

import "fmt"

func main() {
	ch := make(chan int)

	go func() {
		fmt.Println(<-ch)
	}()

	ch <- 1
	ch <- 2
}

The Question

Does this program finish cleanly?

The Output

1
fatal error: all goroutines are asleep - deadlock!

The Explanation

The goroutine receives exactly one value, prints it, and exits. main sends 1, which is received. Then main tries to send 2, but no goroutine is left to receive it. main blocks forever, and since no other goroutine can make progress, the runtime detects a deadlock.

The Common Misconception

Thinking a deadlock only happens when a channel is never used. Often the channel is used correctly once, and the second operation is the one that hangs.

The Takeaway

For every send, count the matching receive. When a goroutine exits, any value expected from it will never arrive.

13. The select Statement ​

The Code

go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)
	ch <- 1

	select {
	case v := <-ch:
		fmt.Println("received", v)
	case ch <- 2:
		fmt.Println("sent")
	}
}

The Question

Which line gets printed?

The Output

Nondeterministic. The output is either received 1 or sent.

The Explanation

The buffer holds one value and has room for one more, so both cases are ready. When several select cases are ready, Go picks one at random. It does not pick the first case in source order. A select with no ready cases blocks, unless it has a default case.

The Common Misconception

Assuming select works like a switch and picks the first matching case.

The Takeaway

Do not depend on which ready case select chooses. If you need priority, check the higher-priority channel in a separate, non-blocking select first.

14. Pointer Receivers vs. Value Receivers ​

The Code

go
package main

import "fmt"

type Counter struct {
	n int
}

func (c Counter) incByValue() {
	c.n++
}

func (c *Counter) incByPointer() {
	c.n++
}

func main() {
	c := Counter{}
	c.incByValue()
	c.incByPointer()
	fmt.Println(c.n)
}

The Question

What does this print?

The Output

1

The Explanation

A value receiver gets a copy of the struct, so incByValue changes only that copy. A pointer receiver gets the address of the original struct, so incByPointer changes c itself. Go lets you call pointer methods on an addressable variable like c, because it takes the address for you.

The Common Misconception

Thinking that calling a method always works on the original value. Value methods work on copies.

The Takeaway

If a method needs to change the struct, or the struct is large, use a pointer receiver. Be consistent: mixing receiver types on one type confuses readers and interfaces.

15. Struct Copying and Shared Fields ​

The Code

go
package main

import "fmt"

type Config struct {
	Name  string
	Items []string
}

func main() {
	c1 := Config{Name: "a", Items: []string{"x"}}
	c2 := c1

	c2.Name = "b"
	c2.Items[0] = "y"

	fmt.Println("c1:", c1.Name, c1.Items)
	fmt.Println("c2:", c2.Name, c2.Items)
}

The Question

Does changing c2.Items affect c1?

The Output

c1: a [y]
c2: b [y]

The Explanation

Assigning c2 := c1 copies the struct field by field. Name is a string, so c2 has its own copy. Items is a slice, and copying a slice copies its header, which points to the same backing array. Both structs now share the same items.

The Common Misconception

Thinking a struct copy is a deep copy. Only value fields are copied. Slices, maps, pointers, and channels are shared.

The Takeaway

When you need an independent copy, copy the slices and maps inside the struct too.

16. Panic and Recover ​

The Code

go
package main

import "fmt"

func main() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("recovered:", r)
		}
	}()

	fmt.Println("before panic")
	panic("boom")
	fmt.Println("after panic")
}

The Question

Is after panic ever printed?

The Output

before panic
recovered: boom

The Explanation

panic stops the normal flow of the function right away, so after panic never runs. The runtime then runs deferred functions while unwinding the stack. recover returns the panic value only when it is called directly inside a deferred function. That is what stops the panic here.

The Common Misconception

Thinking recover works anywhere, or that it can catch panics from a different goroutine. A panic in one goroutine must be recovered in that same goroutine.

The Takeaway

Use panic for programmer errors and unrecoverable states. Return error values for expected failures like bad input or a missing record.

17. Comparable and Non-Comparable Types ​

The Code

go
package main

import "fmt"

func main() {
	type Person struct {
		Name string
		Tags []string
	}

	p1 := Person{Name: "a", Tags: []string{"x"}}
	p2 := Person{Name: "a", Tags: []string{"x"}}

	// Uncommenting the next line causes a compile-time error:
	// fmt.Println(p1 == p2)

	fmt.Println(p1.Name == p2.Name)
}

The Question

Does this compile if the commented line is enabled?

The Output

true

With the comparison enabled, the program does not compile:

invalid operation: p1 == p2 (struct containing []string cannot be compared)

The Explanation

A struct can be compared with == only if every field can be compared. A slice field makes the whole struct non-comparable. The same rule applies to maps and functions. The error comes from the compiler, before the program runs.

The Common Misconception

Assuming structs always compare field by field. That only works when all fields are comparable.

The Takeaway

If you need to compare or use a value as a map key, make sure its fields are comparable, or compare the specific fields you care about.

18. Errors and Error Wrapping ​

The Code

go
package main

import (
	"errors"
	"fmt"
)

func main() {
	err := errors.New("boom")
	wrapped := fmt.Errorf("failed to save: %w", err)

	fmt.Println(errors.Is(wrapped, err))
	fmt.Println(errors.Unwrap(wrapped) == err)
}

The Question

What do the two Println calls print?

The Output

true
true

The Explanation

The %w verb in fmt.Errorf wraps the original error and keeps it in the chain. errors.Is walks that chain and checks each error for a match. errors.Unwrap returns the next error in the chain, which is the original err here.

If you used %v instead of %w, the message would look the same, but the chain would be lost, and both checks would return false.

The Common Misconception

Thinking fmt.Errorf with %v and %w produce the same result. The text is the same, but only %w keeps the error you can check later.

The Takeaway

Use %w when callers may need to check the underlying error. Use errors.Is for sentinel values and errors.As for typed errors.

19. Common Concurrency Mistakes: Data Races ​

The Code

go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var n int
	var wg sync.WaitGroup

	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			n++
			wg.Done()
		}()
	}

	wg.Wait()
	fmt.Println(n)
}

The Question

Should this always print 1000?

The Output

Nondeterministic. It often prints a number below 1000, such as 987. Running go run -race reports a data race on n.

The Explanation

n++ is not one step. It reads n, adds 1, and writes the result back. Two goroutines can read the same value before either writes, so one increment gets lost. The WaitGroup makes sure main waits for every goroutine. It does not protect n.

The Common Misconception

Thinking that a counter is safe because the goroutines finish before printing. The wait fixes timing, but not the race.

The Takeaway

Protect shared state with sync.Mutex, or use sync/atomic for simple counters. Run tests with -race to catch these bugs early.

20. Compilation Errors vs. Runtime Panics ​

The Code

go
package main

import "fmt"

func main() {
	// Uncommenting the next line causes a compile-time error:
	// var n int = "hello"

	s := []int{1, 2, 3}
	fmt.Println(s[10])
}

The Question

Which problem is caught before the program runs, and which one happens at runtime?

The Output

panic: runtime error: index out of range [10] with length 3

The Explanation

A type mismatch like var n int = "hello" is found by the compiler, so the program will not build at all. The index s[10] is only checked when the program runs, so the program compiles and then panics.

The Common Misconception

Assuming that a program which builds is safe. Many common bugs, such as bad indexes, nil dereferences, and writes to nil maps, only appear at runtime.

The Takeaway

Let the compiler catch what it can. Write tests that exercise the code paths where runtime panics can happen.

21. The range Loop Copies Each Element ​

The Code

go
package main

import "fmt"

type User struct{ Name string }

func main() {
	users := []User{{"a"}, {"b"}}

	for _, u := range users {
		u.Name = "x"
	}
	fmt.Println(users)

	for i := range users {
		users[i].Name = "x"
	}
	fmt.Println(users)
}

The Question

Does the first loop change the slice?

The Output

[{a} {b}]
[{x} {x}]

The Explanation

In for _, u := range users, u is a copy of each element. Changing u.Name changes only that copy. The second loop changes the element through the index, users[i], so the slice is updated.

The Common Misconception

Assuming u is a reference to the element, as it would be in some other languages.

The Takeaway

If you need to change elements in a range loop, either index the slice or use a slice of pointers, such as []*User.

22. Shadowed Named Results and Bare return ​

The Code

go
package main

import (
	"fmt"
	"strconv"
)

func parse(s string) (n int, err error) {
	if s != "" {
		n, err := strconv.Atoi(s)
		if err != nil {
			return
		}
		_ = n
	}
	return n, err
}

func main() {
	fmt.Println(parse("12"))
}

The Question

Does this compile and run?

The Output

It does not compile. The compiler reports:

result parameter n not in scope at return
result parameter err not in scope at return

The Explanation

Inside the if block, n, err := declares new variables that hide the named results. A bare return would return the named results, which are not the variables in scope at that point. Go refuses to compile this because the code is ambiguous.

The Common Misconception

Thinking that := reuses the existing variable when one with the same name is already declared. It only reuses variables declared in the same scope.

The Takeaway

Use = instead of := when assigning to named results, or return the values explicitly.

23. Integer Overflow Wraps Silently ​

The Code

go
package main

import "fmt"

func main() {
	var x uint8 = 255
	x++

	var y int8 = 127
	y++

	fmt.Println(x, y)
}

The Question

Does Go raise an error when these integers overflow?

The Output

0 -128

The Explanation

Go integer arithmetic wraps around silently. uint8 goes from 255 back to 0. int8 goes from 127 to -128. No panic or error happens, and the compiler does not warn about the runtime overflow.

The Common Misconception

Assuming that a value larger than the type's maximum is caught automatically, as in some other languages.

The Takeaway

Check input ranges before arithmetic on small integer types, especially for amounts, sizes, and counters in payment or quota code.

24. Strings Are Bytes, Not Characters ​

The Code

go
package main

import "fmt"

func main() {
	s := "héllo"
	fmt.Println(len(s), len([]rune(s)), s[1])

	for i, r := range s {
		fmt.Print(i, ":", string(r), " ")
	}
	fmt.Println()
}

The Question

What are the three numbers on the first line, and what indexes does the range loop produce?

The Output

6 5 195
0:h 1:é 3:l 4:l 5:o

The Explanation

len(s) counts bytes, so é takes 2 bytes in UTF-8, which makes the length 6. []rune(s) converts to characters, which gives 5. s[1] returns a single byte, the first byte of é, which is 195. A range loop over a string decodes one character at a time, and i is the byte offset where each character starts, so the index skips from 1 to 3.

The Common Misconception

Assuming s[i] is the i-th character, or that len counts characters.

The Takeaway

Use range or []rune when you care about characters. Use len and indexing only when you really want bytes, as with raw protocol data.

25. Receiving and Sending on Closed Channels ​

The Code

go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	ch <- 1
	close(ch)

	v, ok := <-ch
	fmt.Println(v, ok)

	v, ok = <-ch
	fmt.Println(v, ok)

	ch <- 2
	fmt.Println("unreachable")
}

The Question

What do the first two lines print, and does the last send succeed?

The Output

1 true
0 false
panic: send on closed channel

The Explanation

A closed channel still delivers values that were already buffered. After that, every receive returns the zero value and ok == false. Sending on a closed channel always panics, so the last line never runs.

The Common Misconception

Assuming a receive on a closed channel blocks, or that closing a channel stops all further sends from the runtime.

The Takeaway

Only the sender should close a channel. Use the ok value in receives to detect closure.

26. A Nil Channel Blocks Forever ​

The Code

go
package main

import "fmt"

func main() {
	var ch chan int

	select {
	case v := <-ch:
		fmt.Println("got", v)
	default:
		fmt.Println("default")
	}
}

The Question

Does the program block on the select, or does it print one of the cases?

The Output

default

The Explanation

A nil channel is never ready for send or receive. Inside a select, a case on a nil channel is simply skipped. Here there is no other ready case, so the default case runs. Without the default, the same select would block forever.

The Common Misconception

Thinking a nil channel behaves like a closed one, or that it returns an error.

The Takeaway

A nil channel is a useful way to turn off a select case. Set the channel to nil once it is finished, and the case stops firing.

27. Method Values Copy the Receiver ​

The Code

go
package main

import "fmt"

type Counter struct{ n int }

func (c Counter) Show() { fmt.Println(c.n) }

func main() {
	c := Counter{n: 1}
	show := c.Show

	c.n = 2
	show()
	c.Show()
}

The Question

What do the two calls print?

The Output

1
2

The Explanation

c.Show is a method value. When it is evaluated, Go copies the value receiver. show keeps the copy with n == 1, so changing c.n afterward does not affect it. The direct call c.Show() uses the current c, where n == 2.

The Common Misconception

Thinking a stored method value always sees later changes. With a value receiver, the struct is copied when the method value is created. With a pointer receiver, the pointer is kept, so later changes are visible.

The Takeaway

With a value receiver, a method value is a snapshot. If you want it to see later changes, use a pointer receiver.

28. Pointer Receivers and Interface Satisfaction ​

The Code

go
package main

import "fmt"

type Speaker interface{ Speak() string }

type Dog struct{}

func (d *Dog) Speak() string { return "woof" }

func main() {
	var s Speaker = Dog{}
	fmt.Println(s.Speak())
}

The Question

Does this compile?

The Output

It does not compile:

cannot use Dog{} (value of struct type Dog) as Speaker value in variable declaration: Dog does not implement Speaker (method Speak has pointer receiver)

The Explanation

The method set of a value type Dog includes only methods with value receivers. Speak has a pointer receiver, so only *Dog implements Speaker. The fix is to store a pointer: var s Speaker = &Dog{}.

The Common Misconception

Assuming that because Go can call pointer methods on addressable variables, values also satisfy interfaces that need pointer methods. The automatic address-taking works for method calls, not for interface assignment.

The Takeaway

If a type has any pointer-receiver methods, usually use &T{} when you need it as an interface.

29. Context Timeouts and the Winning select Case ​

The Code

go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Millisecond)
	defer cancel()

	select {
	case <-time.After(time.Second):
		fmt.Println("done")
	case <-ctx.Done():
		fmt.Println(ctx.Err())
	}
}

The Question

Which case runs, and what is printed?

The Output

context deadline exceeded

The Explanation

The context expires after 10 milliseconds, long before the 1-second timer fires. ctx.Done() closes at that point, so its case is ready first and select takes it. ctx.Err() then reports why the context stopped.

The Common Misconception

Thinking time.After cancels the work when the timeout runs out. It only creates a timer channel. It does not stop anything that is already running.

The Takeaway

Pass the context into the work itself, so the work can stop. A select on ctx.Done() only tells your code to stop waiting.

30. omitempty Drops Zero Values ​

The Code

go
package main

import (
	"encoding/json"
	"fmt"
)

type Payment struct {
	Amount int  `json:"amount,omitempty"`
	Paid   bool `json:"paid,omitempty"`
}

func main() {
	b, _ := json.Marshal(Payment{Amount: 0, Paid: false})
	fmt.Println(string(b))
}

The Question

What JSON does this produce?

The Output

{}

The Explanation

omitempty leaves out a field when it has its zero value. 0 and false are both zero values, so both fields disappear. A client that receives {} cannot tell "amount is zero" apart from "amount was not sent".

The Common Misconception

Thinking omitempty only hides empty strings and nil slices. It also hides numeric zeros and false, which matters a lot for payment and flag fields.

The Takeaway

For fields where zero is a real value, use a pointer (*int, *bool) or drop omitempty, so the client always gets the field.

31. Package Variable Initialization Order ​

The Code

go
package main

import "fmt"

var a = b + 1
var b = f()

func f() int {
	fmt.Println("f called")
	return 10
}

func init() {
	fmt.Println("init", a, b)
}

func main() {
	fmt.Println("main", a, b)
}

The Question

In what order do the initializers and init run, and what is a?

The Output

f called
init 11 10
main 11 10

The Explanation

Go initializes package-level variables by dependency, not by the order they appear in the file. a depends on b, so b = f() runs first. That prints f called. Then a becomes b + 1, which is 11. Only after all package variables are set does init run, and then main.

The Common Misconception

Assuming package variables are initialized strictly top to bottom. Here a is written first but is set last.

The Takeaway

Keep package-level initializers simple and free of side effects. Move work like opening connections into an explicit constructor called from main, so startup order is easy to follow.

Real-World Lessons ​

These traps rarely show up in toy programs. They show up in production code:

  • Unexpected data changes: a helper function slices a request body and modifies it, which silently changes data another handler is still using.
  • Lost updates: a shared counter or cache without a mutex loses writes under load, and the bug only shows up in staging traffic.
  • Hanging services: a goroutine sends on a channel nobody reads anymore, so the request stalls and the connection pool slowly fills up.
  • Confusing API responses: a nil slice marshals to null, and a client that expects [] crashes on its own side.
  • Hidden error loss: a function returns a typed nil pointer as error, so the caller takes the success path and continues with bad state.

When you debug one of these, start with the questions from this post. Which value is shared? Which goroutine owns the write? Which channel has no receiver? Which interface value is actually nil?

Conclusion ​

Most Go traps come from a few ideas: slices and maps share memory, defer captures values when it is registered, a typed nil is not a nil interface, and goroutines run without a fixed order unless you coordinate them.

Don't just read these examples. Paste them into a file, run them, change the snippets, and predict the result before you run them again. Run them with -race and see what the detector reports. The fastest way to remember a trap is to hit it yourself once.
